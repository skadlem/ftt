## Problem Statement
PMOS-style agent teams (planner, implementer, reviewer) run on big API models. The bill scales with every loop. Goal: a cheap local PMOS where role-tuned small models match big-model quality, starting with the planner as systems designer/architect.

## What Makes This Cool
A local planner that designs systems as well as a big model — the "whoa" demo is the same PMOS task, same plan quality, near-zero marginal cost, on your own hardware. Vision (not scope): a self-improving team with more narrow roles (tester, debugger, docs, triage) and smart routing, retrained from its own review feedback. Nothing in the wedge depends on the vision.

## Definitions
- Role behavior: how the model acts in the role (planner decomposes and questions; reviewer challenges; implementer obeys spec).
- Role competence: skill at the role's substance (planner = systems-design judgment).
- PMOS task: one planner→implementer→reviewer loop on a real coding task, scored at the plan stage.
- Curated: human-filtered against the eval rubric before training use.
- Near-zero marginal cost: no per-token API spend at inference; local electricity/hardware only.

## Constraints
- First wedge is ONE role: planner (architect). Implementer/reviewer stay off-shelf until the thesis is proven.
- Bar: planner output as good as a big model at planning, maybe better.
- Training target is role behavior + role competence (may include domain knowledge), not domain knowledge alone.
- Evals on PMOS tasks decide train-vs-prompt, not assumptions.

## Approaches Considered
### Approach A: Prompt-only planner (ruled out as wedge — kept as baseline)
Ready 8B/27B-class small model (exact HF IDs pinned with the base candidates) with architect system prompts, no training, plus eval harness. Rejected as the vehicle because the bar is match-or-beat big-model planning and prompting alone rarely closes that gap; kept as the baseline every tuned version must beat — and as the G0 test that can kill training before it starts.
### Approach B: LoRA-tuned planner on curated design traces (chosen, core method)
QLoRA fine-tune (4-bit base) on an 8B-class model — the only size that fits the chosen free-tier Kaggle/Colab GPU (T4/L4, 16GB). A 27B-class model stays in the plan as an inference-only reference baseline, never a training target: it answers "can tuning beat size" for free. Exact HuggingFace repo IDs pinned before training.
### Approach C: Distill planner from big-model traces (chosen, data source)
Teacher: the open-weight qwen3.8-max route (user decision, 2026-09-04). Open-weight keeps the G3 release ToS-clean by construction and its API serves real thinking tokens, which closed proprietary teachers do not. Teacher generates 200-500 plans on PMOS tasks; traces are reasoning-inclusive (chain-of-thought kept, not final-plan-only) so the student learns planning process, not just outputs.

## Recommended Approach
B+C combined: QLoRA-tune the 8B planner (B = method) on distilled open-weight-teacher plan traces (C = data at scale), eval-gated blind-pairwise against both the prompt-only baseline (A) and the teacher, with the 27B reference baseline answering "can tuning beat size" for free. Assumed residual gap the tuning must close: the untuned base trails the teacher on general coding (~4pts on SWE-bench class benchmarks) and the planning-specific gap is unquantified until the eval harness runs — the harness measures it first, training starts only after. Ladder after the wedge (reviewer, then implementer, then narrow roles) is direction, not plan: each step needs its own gate.

## Success Criteria — staged go/no-go gates
Scoring method (user decision, 2026-09-04): NO absolute 0-100 judge scores. Plans are compared pairwise, blind (source stripped, order randomized), by an LLM judge from a different model family than the teacher — a same-family judge scores its own style higher, which would fake a G1 pass. Gate on win-rate vs teacher and vs baseline, paired significance (p<0.05, n>=50), plus a human spot-check of n=8 random pairs to keep the judge honest. Threshold numbers are pre-registered in the harness spec before any training run. No moving goalposts after seeing results.

- **G0 — Is there a gap worth closing?** Harness runs teacher vs prompt-only baseline (8B-class and 27B-class, both inference-only) on the tiered eval set (D14). If baseline is statistically indistinguishable from teacher, training is pointless for this role: ship prompting, save the compute.
- **G1 — Did training close the gap?** Tuned 8B planner non-inferior to teacher (win-rate >= ~45%, pre-registered) AND beats the same-size prompt-only baseline (win-rate >= ~65%, pre-registered). The stated bar "maybe even better" lives here as the stretch: match = pass, exceed teacher = win.
- **Length-bias control (user decision 2026-09-04, outside voice):** every arm is ALSO judged as a trimmed final-plan view — reasoning stripped, format normalized across arms, plan length capped and reported per arm. Rationale: the student learns verbose CoT; a terse prompt-only baseline judged against it measures verbosity, not judgment, which would make G0's kill-gate near-uncloseable and inflate G1. Primary metric is the format-matched comparison; full-trace (reasoning-inclusive) scoring is reported as secondary, never gates.
- **Arm placement (user decision, D13):** the 27B reference arm runs via the existing Qwen3.8-27B API route (free pool), never on the 16GB notebook GPU — Q4 weights leave no KV headroom for long-context plan generation there. Answers "can tuning beat size" at zero cash cost; teacher remains the ceiling anchor.
- **G2 — End-to-end loop quality.** An isolated plan score can lie. Run the full PMOS team (tuned planner + off-shelf implementer and reviewer) on the same tasks: end-to-end task success must not be worse than the big-model-planner team.
- **G3 — Cost and portability.** Full loop runs locally, zero per-token cost, documented throughput and wall-clock. Open-source release is post-G3; training data is ToS-clean by construction (open-weight teacher).
- **Tiered eval set (user decision 2026-09-04, D14):** CORE = all recoverable real tasks (6-7 expected), the trust anchor. RING = teacher-generated tasks from task families NOT in the train pool (family-disjoint, not just instance-disjoint), sized for n>=50 combined. Every gate result is reported per tier; a pass requires the ring to clear the pre-registered threshold AND the core to not contradict it (no core loss-win with ring win-loss — if tiers diverge, stop and adjudicate, don't average).
- **Contamination rule (all gates):** eval tasks (core real + ring) are frozen (hash-checked) before trace sampling and hard-disjoint from the training set. Training traces are teacher-generated variants tagged `synthetic` — a synthetic task can never share an id or wording with a frozen eval task (checked at write time, not at gate time). Ring tasks additionally exclude train-pool task FAMILIES (the generator's family registry is committed alongside the fixtures).
- **Kill conditions.** Two tuning rounds (one round = one data revision + one QLoRA run) failing G1 → fall back to prompting and write up why. Teacher-API spend passing the Hardware & budget estimate → stop sampling, rescope traces. A failed wedge says so loudly; it does not wander.
